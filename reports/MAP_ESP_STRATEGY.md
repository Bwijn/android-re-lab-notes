## 1. The Discovered ESP Target Functions
Based on the analysis of the `lolm_dump.cs` IL2CPP export, we have bypassed `IsActorAlwaysVisibleInMiniMap` (which is likely blocked by Server-Side Fog of War or unused for live enemy players) and identified the 3 most promising top-level visibility controls. 

If we apply our Ring-0 Stealth Patch (`MOV W0, #1; RET`) to any of these, we may force the game client to render the target regardless of FOW state.

### Candidate A: The Root Visual Switch
*   **Class**: `FrameEngine.Visual.BattleActorVisi`
*   **Method**: `System.Boolean get_ShouldBeVisible()`
*   **Why it's suspicious**: This is the top-level property in the visual representation (`Visi`) of a battle actor. If we force this to `True`, the engine might completely bypass all culling logic (camera frustum, FOW, stealth) and force the renderer to draw the champion model and UI.

### Candidate B: The Fog of War Override
*   **Class**: `FrameEngine.Logic.ActorComponentFow`
*   **Method**: `System.Boolean IsFowIgnoreBlock()`
*   **Why it's suspicious**: This method exists inside the Fog of War (`Fow`) component. It literally translates to "Does this actor ignore FOW blocking?". This is exactly the behavior of *True Sight* (e.g., Pink Wards, Twisted Fate ultimate). Forcing this to `True` for enemies could grant permanent True Sight.

### Candidate C: The MiniMap Icon Specific Override
*   **Class**: `UIMiniIconBaseCtrl`
*   **Method**: `System.Boolean IsVisible(FrameEngine.Visual.BattleActorVisi actor)`
*   **Why it's suspicious**: This is the UI controller specifically responsible for drawing icons on the Minimap. Modifying this could decouple the Minimap rendering from the actual 3D world FOW logic, drawing enemy icons even if their 3D models are culled.

## 2. How to Locate Offsets in IDA Pro (Symbol Restoration)
The `libil2cpp_decrypted.so` you dumped is a strictly stripped ELF binary. This is why all functions appear as `sub_XXX` in IDA Pro—the symbol table (`.symtab`) has been removed by the compiler.

The metadata (`metadata_dumped.dat`) contains the real names, but IDA doesn't know how to link them. Here is the standard IL2CPP Reverse Engineering workflow to fix this:

### Step 1: Locate the Il2CppDumper Output
When you originally ran `Il2CppDumper` to generate `lolm_dump.cs`, the tool should have also generated several other files in the same output directory. You need to find:
*   `script.json` (Contains the mapping of RVA -> Function Name)
*   `ida_with_struct_py3.py` (or `ida.py`)
*   `il2cpp.h` (Optional, for struct definitions)

### Step 2: Run the Python Script in IDA Pro
1. Open your `libil2cpp_decrypted.so` in IDA Pro and wait for the initial auto-analysis to finish.
2. Go to **File -> Script file...** (or press `Alt + F7`).
3. Select `ida_with_struct_py3.py` (or `ida.py`).
4. IDA will prompt you to select a JSON file. Choose the `script.json` generated by Il2CppDumper.
5. IDA will prompt you for the C++ header file. Choose `il2cpp.h`.

### Step 3: Wait for Symbol Restoration
IDA will now run the script, which iterates through `script.json` and automatically renames every single `sub_XXXXXXXX` function to its massive, fully qualified IL2CPP name (e.g., `FrameEngine_Visual_BattleActorVisi__get_ShouldBeVisible`).

It will also apply the correct C# structures to the memory layout.

### Step 4: Search for the Targets
Once the script finishes:
1. Open the **Functions Window** in IDA (`Shift + F3`).
2. Search (using `Ctrl + F`) for the keywords:
   * `get_ShouldBeVisible`
   * `IsFowIgnoreBlock`
   * `UIMiniIconBaseCtrl`
3. Double-click the function to jump to its assembly.
4. Note the **Offset (RVA)** at the top of the function.

Once you have the offset (e.g., `0x1234568`), provide it to me, and we will update `client.c` to launch the Stealth Patch pipeline directly onto that address!
